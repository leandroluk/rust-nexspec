---
title: "Phase 19 · Retrieval Enrichment"
description: LLM summaries per file, indexed per language, so questions in prose can find code.
---

`nexspec enrich` closes the gap between a question in prose and the identifiers in code. It is opt-in and never runs on its own.

Source: `.specs/features/retrieval-enrichment/`

## How it works

1. **Select.** Indexed TS/JS, Python, Go, Rust and Markdown files, honouring `.gitignore`. Never `.env*`, keys, certificates, binaries or generated code. The first 2500 characters of each file are scanned for secrets (private keys, cloud tokens, literal passwords and the like). A file that matches is **sent with the secrets masked**: private key blocks become `[REDACTED PRIVATE KEY]`, tokens and credential literals become `[REDACTED]` (`password = "[REDACTED]"`), the rest of the code is untouched, and the masked text is scanned again; if anything still looks like a secret the file stays home. `--status` lists these files as `sent with secrets masked`. The scan is deliberately blunt (it cannot tell a mock from a real value, and a test file with a fake password is flagged too), which is why masking beats keeping the file back; `--omit-secrets` restores the stricter behaviour of not sending a flagged file at all.
2. **Order.** Most important first: graph degree, links to requirements and tasks, co-change. `--top 20%` or `--top 300` stops early.
3. **Ask.** Batches of files go to the provider (Gemini first, key from `GEMINI_API_KEY`, sent in a header only). One request returns the summary in every language of `--lang`, written natively, not translated.
4. **Ask again.** Files the answer skipped (or whose answer lacks a language) are asked for again, one at a time, once: a crowded request is the usual reason a model skips a file. Network errors and HTTP 429/5xx are retried with back-off inside each request.
5. **Keep.** After every batch the cache is rewritten and the summaries are applied to the index, so Ctrl+C or `--token-budget` lose nothing and repeat nothing.

## Search

The index has one field per language (`summary_en`, `summary_pt`, `summary_ru`, …, every language Tantivy can stem) next to `text`. There is no language detection: a question in any language can match the summary written in that language. `--no-enrich` on `search` and `query` ranks on code text only.

**Questions in prose get the summaries; identifier lookups do not.** A sentence ("how does a user log in to the application": three or more meaningful words, at least one stopword, nothing shaped like an identifier) searches the summaries with weight 2; a keyword list or identifier ("login use case password authenticate", `handleInvoice`, `who calls seed_discovery`) does not touch them. `NEXSPEC_ENRICH_WEIGHT` overrides both (`0` switches the summaries off). Stopwords (English and Portuguese) are dropped from every multi-word question before it is searched, and question text is never read as query syntax (`Synonyms: a, b` is just words). Why: on the reference corpus, applying one weight to everything either did nothing for prose (0.5) or lifted prose recall by 15 points while costing `locate` 10 points of MRR (2.0): identifier-shaped questions already match names, and the summaries only get in their way.

## Cost and control

| Command | What it does |
| --- | --- |
| `enrich --dry-run` | Offline estimate: files, tokens in and out, cost at 20 %, 50 % and 100 % coverage. |
| `enrich --status` | `enrichment: N/M files up to date (en,pt), S stale, P pending`, plus failures, omitted files and accumulated tokens and cost. |
| `enrich --yes` | Skips the confirmation asked on the first use and above 500 000 estimated input tokens. |
| `enrich --token-budget T` | Stops cleanly after `T` tokens as reported by the provider. |
| `enrich --clear` | Deletes the cache. |

Prices come from `NEXSPEC_ENRICH_PRICE_IN` / `NEXSPEC_ENRICH_PRICE_OUT` (USD per million tokens) or a small built-in table; an unknown model is flagged as a guess. Exit code 6 means some files failed and the rest were kept.

## Is it worth it?

`nexspec bench --compare-enrich` runs your corpus twice on the same commit. The summaries may keep a weight above zero only if prose (`behavior`) questions gain at least 15 points of `recall@5`, `locate` MRR drops by at most 2 points and median latency grows by at most 20 %. The report also says how many questions it takes for the enrichment tokens to pay themselves back.

### Measured on the condominium (2026-09-30)

1038 files summarised in English (about 706 thousand tokens, US$ 0.10 with `gemini-flash-lite-latest`), corpus of 32 questions including 8 in prose:

| | without summaries | with summaries |
| --- | --- | --- |
| prose (`behavior`) recall@5 | 40 % | 55 % (+15 points) |
| `locate` MRR | 0.93 | 0.93 |
| `structure` recall@5 | 100 % | 100 % |
| median latency | 86 ms | 60 ms |

All three criteria pass, so the summaries keep their weight. The corpus is small (ten prose questions, and the weight was tuned on it), so treat it as a first confirmation rather than a measured guarantee; add prose questions of your own to `.specs/bench/queries.toml` and run `bench --compare-enrich` on your repository.
